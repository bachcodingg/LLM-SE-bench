# v2: repository-level agentic evaluation

Where this is going, why, and what is actually built.

## Positioning

**Do not build another SWE-bench.** That space is saturated: SWE-bench,
SWE-bench Verified, SWE-bench-java, SWE-PolyBench, SWE-bench Multilingual,
SWE-rebench, SWE-bench Live, and a wave of 2026 additions including
SWE-Refactor, SpecBench and ProjDevBench. A generic issue-resolution
benchmark in 2026 is late.

Three gaps remain, and this project is unusually well placed for all three.

### Gap 1 — Java and the JVM are thin and badly served

SWE-bench-java has 91 instances. SWE-PolyBench has 2,110 total but only 165
in Java. Reported Java resolve rates sit far below Python, and the bottleneck
is largely environmental: EnvBench found the best automated environment
setup method succeeded on **29.5%** of JVM repositories. Most failures happen
before any code is written, which means most of what a Java benchmark
measures is the harness.

A working, deterministic, checkpointable JDK 17 Docker sandbox already
exists here. That is the hard part.

### Gap 2 — refactoring is scored as if it were bug fixing

Almost every benchmark scores pass/fail on tests. For refactoring that is
the wrong objective function, and wrong in an exploitable way: **a
refactoring that changes nothing passes every test.** Behaviour preservation
is necessary and nowhere near sufficient; structural improvement has to be
measured independently.

The instrument for that already exists here too — CK metrics and a 4-level
severity classifier, from the author's thesis.

### Gap 3 — agent evaluation ignores cost and reward hacking

Leaderboards report resolve rate. They rarely report euros. An agent that
solves 5% more tasks at 8× the cost is not obviously better and, for any
team with a budget, is worse.

Separately, long-horizon agents cheat: they edit tests, hardcode expected
values, swallow exceptions, delete assertions. SpecBench (2026) exists
specifically because of this. Detection is mostly unsolved and mostly not
instrumented.

### The position, in one sentence

> A repository-level agentic benchmark for JVM refactoring that scores on
> three independent axes — behaviour preservation, structural quality
> change, and euros spent — with automatic detection of test tampering.

Defensible, not a reskin of anything that exists, and every component maps
onto work already done.

### M1 — agent harness

Four scaffolds behind one interface, which is the point: `single_shot` (the
v1 baseline), `react`, `plan_then_execute`, and `external` (shell out to
Claude Code or Aider). Most papers compare models and publish conclusions
about models; what they compared was model-plus-their-scaffold. Holding the
model fixed and varying the scaffold is the only way out, and every
trajectory records which one ran.

Also: context compaction before the window fills (with a summary written to
stop the agent repeating what it already tried), prompt-cache breakpoints,
and parallel episodes under a shared locked budget.

### M2 — tool layer

Permission modes (`read_only`, `patch_only`, `full`) so "more access is
better" can be tested rather than assumed. Versioned tool registry whose
fingerprint covers descriptions as well as schemas, because the description
*is* the prompt. Tool-call cost attribution: a result produced at step 2 of a
20-step episode is re-sent 18 more times, which nothing usually measures.

### M3 — task factory

The hardest module and the one with the clearest external value. Mining
filters, reverse-patch construction, FAIL_TO_PASS / PASS_TO_PASS derivation,
build-system detection across Maven and both Gradle DSLs, JDK inference,
offline dependency prewarming, and six admission gates including the
five-run flake check.

**Running it is the remaining project.** See [`roadmap.md`](roadmap.md).

### M5 — structural scoring

Three axes reported separately, never collapsed into one number: behaviour
preserved (tests, public API diff, differential testing), structure improved
(CK deltas with published weights), and not gamed. The anti-gaming guards
exist because deleting code improves every CK metric at once.

### M6 — tamper detection

Three layers: an immutable test manifest (mechanical, cannot false-positive),
static detection on the patch (heuristic, never strikes a solve on its own),
and held-out suites. The headline it produces is **clean solve rate**, and
the gap between it and raw pass rate is a result in itself.

### M7 / M8 — cost and statistics

Cache tiers priced at their own rates, cost-normalised scoring, a budget
simulator that reports statistical power alongside affordability, and a
Pareto frontier with dominated configurations marked. On the statistics side:
unbiased pass@k that refuses to extrapolate, variance decomposition,
clustered bootstrap, and sequential testing with alpha spending.

## What is deliberately not here

- **No mined dataset.** M3's machinery is tested against fixtures. Producing
  150–300 validated instances needs a GitHub token, network access, Docker,
  and hours of Maven and Gradle runs.
- **No LLM-as-judge.** M4's taxonomy is rule-based, with ambiguous cases
  flagged rather than guessed. A judge belongs only where no deterministic
  rule exists, and the agreement between the two has to be reported.
- **No mid-episode resume.** A trajectory is serialisable; an episode is not.
- **No held-out suites in the current tasks.** M6 supports them; the 58
  existing tasks do not have them.
- **Differential testing is boundary-value, not coverage-guided.** It will
  find an off-by-one at zero and will not find a bug needing a specific
  12-character string. Agreement is evidence, not proof, and the result says
  so.

## Reading the results, when they exist

Three numbers, and the gaps between them are the interesting part:

| | |
|---|---|
| **Raw resolve rate** | What every leaderboard reports |
| **Clean solve rate** | Resolve rate minus solutions that cheated |
| **Resolve rate per euro** | What a team with a budget actually needs |

Plus the contamination stratification: pre-cutoff versus post-cutoff resolve
rate, with the gap as the memorisation signal.
